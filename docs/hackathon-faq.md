# Hackathon FAQ Notes

Source: organizer FAQ shared on 2026-05-28.

This document captures organizer guidance that should influence WorkTape planning, submission packaging, and evidence collection.

## Codex / OpenAI Usage

- Codex/OpenAI usage is mandatory as part of the building journey and carries evaluation weight.
- If credits or rate limits become a blocker, other tools may be used, but Codex/OpenAI usage must still be visible.
- "Meaningfully using Codex" means OpenAI tools actively contribute to product-building. Accepted examples include coding assistance, debugging, workflows, prototyping, AI-powered features, research, and development acceleration.
- Direct OpenAI API integration inside the product is not strictly required, but WorkTape already has a stronger path because it uses OpenAI Responses API for workflow video analysis.
- Usage may be tracked through:
  - Organization IDs
  - Build-in-public posts
  - GitHub/activity updates
  - Working documents and progress tracking

## MVP Checkpoint Requirement

By Phase 1, the expected submission includes:

- An MVP with the main features working.
- Clear user flow / product journey.
- A 4-slide pitch deck covering:
  - Problem / pain point.
  - Proposed solution and key features.
  - Tools / tech stack.
  - ICP / ideal customer profile / target audience.

The organizers described the checkpoint as:

- A toy version.
- Rough but functional.
- Basic user flow plus screens working.

## MVP Functionality Bar

- Main features should be working at a basic MVP level.
- The MVP does not need to be polished or production-ready.
- Meaningful implementation progress matters more than completeness.
- Technical blockers and incomplete features are acceptable if progress, direction, and execution are clear.

## Scope Guidance

- Build a lean, working MVP with a clear user flow and core functionality.
- Keep scope tight.
- Prioritize shipping over overbuilding.
- Existing ideas may be extended, but the product should not already be prebuilt.
- Progress will be tracked through working documents, daily updates, GitHub activity, and build-in-public posts.

## Build-In-Public

- Build-in-public updates are mandatory for accountability/tracking.
- Updates do not need to be polished.
- Acceptable evidence includes:
  - Progress screenshots.
  - Looms.
  - GitHub updates.
  - Docs.
  - Work logs.

## Feedback / Mentorship

- Support and mentorship happen through sessions after Phase 1 and Phase 2.
- Product feedback is expected to come through Q&A discussions and guidance sessions.

## WorkTape-Specific Implications

- Keep `codex-usage-log.md` current because organizer tracking explicitly accepts working documents and progress tracking.
- Keep build-in-public artifacts current. Screenshots and short updates are enough; polish is not required.
- For Phase 1 packaging, create or maintain a 4-slide pitch deck in addition to product brief/screenshots/user-flow documents.
- Continue to label saved fallback paths honestly. A partially mocked or fallback-supported MVP is acceptable only if main features show meaningful implementation progress.
- The live OpenAI video analysis path is a scoring advantage, but the demo should still have a deterministic fallback so the user flow does not break during review.
- Friday/Sunday work should prioritize: stable live link, clear product journey, recorded walkthrough, validation notes, build logs, and visible Codex/OpenAI contribution.
